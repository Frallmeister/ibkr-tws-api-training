# Errors, warnings, and informational messages

The callback name `error()` is slightly misleading in the TWS API.

It is used not only for failures, but also for warnings and informational system messages. The startup output from our first example already demonstrated this:

```text
ERROR -1 1787356202800 2104 Market data farm connection is OK:usfarm.nj
ERROR -1 1787356202811 2106 HMDS data farm connection is OK:euhmds
```

Both lines were delivered through `EWrapper.error()`, even though neither represents a failed operation.

## The current Python callback

In current TWS API versions, the callback has the form:

```python
def error(
    self,
    reqId,
    errorTime,
    errorCode,
    errorString,
    advancedOrderRejectJson="",
): ...
```

The main fields to understand for now are:

```text
reqId       -> which request the message belongs to, when applicable
errorTime   -> when the message was generated
errorCode   -> IBKR message/error code
errorString -> human-readable description
```

`advancedOrderRejectJson` is used for additional order-rejection information and belongs to the later orders section.

!!! note
    TWS API 10.33 added `errorTime` as the second callback argument. Older examples on the internet may therefore show a different Python signature.

## `error()` is a message channel

A better mental model is:

```text
TWS / API client
      ↓
error-related or system message
      ↓
EWrapper.error(...)
      ↓
your application decides what it means
```

Do not infer severity from the callback name alone.

Instead, inspect the code, text, request context, and IBKR's error-code documentation.

For example:

```text
2104 -> market data farm connection is OK
2106 -> historical data farm connection is OK
```

IBKR explicitly documents these as notifications rather than true error conditions.

By contrast:

```text
502 -> could not connect to TWS
504 -> not connected
```

represent actual connectivity failures.

## Request-specific versus general messages

Many error callbacks include the `reqId` of the request that caused the message.

Conceptually:

```text
reqMktData(reqId=17, ...)
        ↓
TWS rejects or warns about that request
        ↓
error(reqId=17, ...)
```

That lets the application associate the message with the correct operation.

Some messages are not tied to one request. In those cases IBKR commonly uses:

```text
reqId = -1
```

The 2104 and 2106 startup messages from our first example are examples of this. They describe system/connectivity state rather than a particular API request.

## Where messages can originate

Not every message delivered through `error()` is generated by the same component.

For example, error code 502 can occur when the operating system fails to open the TCP connection to TWS. The API client then delivers that condition through `EWrapper.error()`.

Other messages originate from TWS or IBKR infrastructure.

So the callback is best understood as a common delivery point for error-related and system information, not as proof that TWS itself generated every message.

## Do not treat every message identically

A simple learning script may print every `error()` callback. That is useful because it exposes what the API is doing.

A more robust application will eventually distinguish between categories such as:

```text
informational status
warning
request failure
connectivity failure
order rejection
```

But this does **not** mean maintaining a hard-coded list of every IBKR code inside each example.

For now, the important habit is:

1. read `errorCode` and `errorString`;
2. check whether `reqId` associates the message with a request;
3. look up unfamiliar codes in IBKR's current error-code documentation;
4. decide whether the message actually requires application action.

The later robustness chapters will cover how long-running applications should react to specific connectivity events and failures.

## Why the first example still succeeded

The first example produced several lines beginning with `ERROR`, followed by the requested server time.

The actual flow was:

```text
nextValidId(...)
    ↓
reqCurrentTime()
    ↓
2104 / 2106 status messages
    ↓
currentTime(...)
    ↓
disconnect()
```

The presence of `error()` callbacks did not interrupt the request/response flow. They were simply additional messages processed by the same event loop.

This is another consequence of the asynchronous model covered in the previous chapters: unrelated messages can arrive while another request is active.

## A useful reading strategy

When `error()` fires, ask:

1. **Which code is this?**
2. **Is it tied to a request ID or is it general system state?**
3. **Does IBKR describe it as an error, warning, or notification?**
4. **Does the current operation need to stop, retry, or simply continue?**

Those questions are more useful than treating every call to `error()` as exceptional program termination.

## The mental model to keep

```text
EWrapper.error(...)
        │
        ├── informational notification
        ├── warning
        ├── request-specific failure
        ├── connectivity problem
        └── later: order rejection details
```

The callback name is fixed by the API, but the messages it carries have different meanings and severities.
